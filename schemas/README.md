# Knowledge-graph schema for the Corvane corpus

This is a hand-written schema for the Corvane Mutual claims-platform modernisation: the move from the legacy CLARA mainframe (COBOL/CICS/DB2) to the Claims Hub microservices. Load it into a schema-driven extraction tool before you ingest the corpus. The graph that comes out is then audited against `questions/graph_expectations.yaml`.

## Files

| File | What it is for | Edited by hand? |
|---|---|---|
| `corvane_claims.jsonld` | **The schema.** RDFS/OWL in JSON-LD: 28 `owl:Class`, 60 `owl:ObjectProperty`, 67 `owl:DatatypeProperty`. It is self-contained (inline `@context`, namespace `https://example.org/corvane/claims#`, prefix `cc:`). This is the file to import. | Yes. It is the only source. |
| `corvane_claims.ttl` | The same schema as Turtle. | No. Generated by `validate_schema.py --emit-ttl`. |
| `corvane_claims.rdf` | The same schema as RDF/XML. | No. Generated by `validate_schema.py --emit-ttl`. |
| `terminology_variants.yaml` | Canonical term → the variants documents use instead ("loss adjuster" for Claims Assessor, "peril" for Claim Type, …), with families, notes and where each term lands in the schema. The scorer and the graph audit read it. **Do not import it.** | No. Generated from `world/data/glossary.yaml` by `validate_schema.py --emit-variants`. |
| `schema_assistant_prompt.md` | A short prompt to paste into a product's schema-assistant chat, so the assistant-built schema can be compared with this one. It also has follow-up prompts that check whether a rename is really saved. | Yes. |
| `validate_schema.py` | Validates the JSON-LD and emits the derived files. | Yes. |

## Importing

1. Use the product's schema import with `corvane_claims.jsonld`.
2. If it rejects JSON-LD, try `corvane_claims.ttl`, then `corvane_claims.rdf`. The three files hold the same triples, and the validator proves it.
3. After the import, check that the product shows the class labels (for example "Claims Assessor") and the UPPER_SNAKE relationship labels (for example `WRITES_TO_TABLE`). Some tools show the IRI local names instead (`ClaimsAssessor`, `writesToTable`). The graph audit treats both forms as equal.
4. Three relationships (`PART_OF_SYSTEM`, `IMPLEMENTS_RULE`, `RENAMED_TO`) and some datatype properties allow more than one subject class. They express this with `owl:unionOf`. If the import drops or rejects those domains, record that as a finding. Don't edit the schema to work around it.

Do not import `terminology_variants.yaml`. The schema holds canonical terms only, because the test measures how extraction copes when documents use other words.

## Validating and regenerating

```
.venv/bin/python -I schemas/validate_schema.py                    # check everything, change nothing
.venv/bin/python -I schemas/validate_schema.py --emit-ttl         # after editing the JSON-LD
.venv/bin/python -I schemas/validate_schema.py --emit-variants    # after the glossary changes
```

The validator parses the JSON-LD with rdflib (`format='json-ld'`) and checks the following:

- Every class and property has exactly one `rdfs:label` and one `rdfs:comment`.
- Labels follow the naming rules:
  - A class label is the canonical name and matches its IRI ("Claims Assessor" ↔ `cc:ClaimsAssessor`).
  - A relationship label is the UPPER_SNAKE form of its camelCase IRI (`REPORTS_TO` ↔ `cc:reportsTo`).
  - A datatype property label equals its IRI local name.
- Every object property has one domain and one range, and each is a declared class or an `owl:unionOf` of declared classes.
- Every datatype property has a declared domain and an `xsd:` range.
- No relationship name is generic (`BELONGS_TO`, `RELATES_TO`, `HAS_MANY`, `DEPENDS_ON`, `HAS`, …).
- Every class and relationship that the brief requires is present.
- No glossary variant appears in any label, `skos:altLabel` or comment. Each variant is checked as a whole word, and a variant that sits inside a canonical term ("assessor" inside "Claims Assessor") is allowed.
- `harness/graph_audit.py` reads exactly these 28 class names from the JSON-LD.
- The `.ttl` and `.rdf` files are graph-isomorphic to the JSON-LD.
- `terminology_variants.yaml` is up to date with the glossary.
- This README has a row for every class, relationship and datatype property, with the schema's domain and range.

The emitted files are byte-stable across runs.

## Modelling decisions

- **Canonical terms only.** Class labels use the glossary's canonical schema terms ("Claims Assessor", "Claim Type"). Where another canonical term is a value rather than a type, it appears in the comments of datatype properties, for example "Fraud Score", "Reserve", "Excess" and "First Notice of Loss". The few `skos:altLabel`s are technical synonyms, never document variants: "COBOL Program", "JCL Job", "BMS Map", "Microservice", "Architecture Decision Record", "Regulatory Circular", "Regulatory Return" and "Organization".
- **No world instances in the schema.** Comments describe each type in general terms. Instance examples live only in this README, so the schema gives the extractor no hints about the answers.
- **Rules and versions.** A rule is a `BusinessRule` node (`BR-FRD-031`). It has one `RuleVersion` node per version (`HAS_VERSION`), for example "BR-FRD-031 v2".
  - Wording and parameters are datatype properties on the version: `ruleText`, `threshold`, `tier3Threshold`, `amount`, `currency`, `status`, `effectiveFrom`, `effectiveTo`, `approvedOn` and `version`. A draft version has no effective dates.
  - A newer version of the same rule points at the older one with `SUPERSEDES_VERSION` (v2 → v1). `SUPERSEDES` is reserved for one rule id replacing another (BR-FRD-031 → BR-FRD-012).
  - The links that don't change between versions sit on the rule: `IMPLEMENTS_RULE`, `GOVERNED_BY`, `APPLIES_TO_*` and `OWNS_RULE`. `APPROVED_BY` sits on the version.
  - So "the Tier-3 threshold since 2026-10-01" is the `tier3Threshold` (60) of the version whose `effectiveFrom` is 2026-10-01.
- **Time-dependent facts.** OWL has no edge properties, so the schema has no validity dates on edges. The following facts are true only for a period: `REPORTS_TO`, `LEADS`, `HEADS_DEPARTMENT`, `MEMBER_OF`, `OWNS_PROCESS`, `OWNS_SERVICE`, `jobTitle`, `status` and `schedule`. A graph can therefore hold both the stale value and the current one; Calloway, Quill and Lindahl as owners of the subrogation stage is an example. Expectation edges carry an `as_of` date for this reason.
- **Renames.** A rename can be recorded as a `RENAMED_TO` edge (FRAUDNET → Sentinel) or by merging the two names into one node. The graph audit accepts either. The expectations skeleton lists both forms; curate it down to one.
- **Claims Assessor** is a role type that covers internal employees and panel firms. An internal Claims Assessor (Mohammed Saleem) may also appear as a `Person`, and the two nodes are not merged automatically. `PROVIDED_BY_FIRM` links a Claims Assessor to the firm that provides them, or to the insurer for internal ones.
- **Tables.** `WRITES_TO_TABLE` and `READS_FROM_TABLE` are COBOL CRUD links (Program → Database Table). A Claims Hub service is linked to its own PostgreSQL tables with `OWNS_TABLE`, since each service has its own database.
- **RACI.** `RESPONSIBLE_FOR` (team, R) and `ACCOUNTABLE_FOR` (person, A) are modelled. Consulted and Informed are not modelled.
- **Not modelled:** committees, meetings and meeting decisions (DEC-xxx), documents, Policyholder and Claims Handler (both are roles, and handlers appear as `Person` nodes with a `jobTitle`), and glossary concepts such as Bordereau. See `schema_targets` in `terminology_variants.yaml`.

## Graph expectations

`harness/graph_audit.py expectations-skeleton` reads the class names from `corvane_claims.jsonld` and writes `questions/graph_expectations.draft.yaml` using them. The audit compares type and relationship names without regard to case or punctuation. For example, `REPORTS_TO`, `reportsTo` and `PERSON_REPORTS_TO_PERSON` all match, so expectations can use either the labels or the IRIs.

The skeleton's 22 `Term` merge groups come from the glossary, and this schema has no class for them. Drop them, or retype each one using `schema_targets` in `terminology_variants.yaml`. For example, Counter-Fraud & SIU becomes a `Team`, CLARA and Claims Hub become `System`, and First Notice of Loss and Settlement become `ProcessStage`.
