Record version

RSVMOVE carries a record version byte (RM-REC-VERSION, value 02) since 2025-04-30 (CHUB-142). Consumers validate it before processing.

Change control

Any change to the RSVMOVE layout or to the extract needs signed impact assessments from every downstream consumer (CHUB-144). The unannounced widening of RM-AMOUNT under CHUB-138 broke the GL reserve journals in INC-2025-0412.

Extract logic

SELECT MOVE_ID, RSV_ID, CLAIM_ID, MOVE_TS, MOVE_TYPE_CD, MOVE_AMT, MOVE_GBP_AMT
  FROM CLR.T_RESERVE_MOVEMENT
 WHERE EXTRACTED_FLAG = 'N'
 ORDER BY CLAIM_ID, MOVE_ID;
-- after a successful MQPUT of each record:
UPDATE CLR.T_RESERVE_MOVEMENT
   SET EXTRACTED_FLAG = 'Y', EXTRACT_RUN_ID = :WS-RUN-ID
 WHERE MOVE_ID = :WS-MOVE-ID;

Restart: rerun the whole job; CLRRS170 only extracts rows with EXTRACTED_FLAG = 'N', so a rerun does not resend records that were already put to the queue.

Monitoring

  • Queue depth on CLR.RSVMOVE.OUT is alerted as a share of the queue's maximum depth.
  • Consumer lag on claims.reserve.movement.v1 is alerted for reserve-engine (see INC-2026-0311).
  • A missing extract dataset is reported by the Batch Scheduler as a late job.
  • As a rule, reprocessing of CLX-IF-042 is idempotent at record level, so replay is safe after an outage.

FAQ

Can I rerun the extract?
Yes. The extract only picks up rows with EXTRACTED_FLAG = 'N', so a rerun does not resend records.
Who must approve a layout change?
Every downstream consumer: GL (CLX-IF-043), CDW (CLX-IF-044), ReCede (CLX-IF-047) and the Kafka bridge (CLX-IF-049).
Which return depends on this interface?
NISA-TP2, through CLX-IF-043 and CLX-IF-051.
Where is the record layout kept?
Copybook RSVMOVE in the CLARA source baseline.

Operations

Access to CLX-IF-042 payloads is restricted to named support roles, and access is reviewed quarterly. The message layout of CLX-IF-042 is versioned, and dependent interface owners are told about any change in advance. Test evidence for CLX-IF-042 is held with the release record, together with the reconciliation output. CLX-IF-042 is monitored through the standard integration dashboards and failures page the integration on-call engineer.

Error codes are mapped to the shared catalogue so that alerts can be grouped by cause. Poison messages are parked rather than retried indefinitely, and a ticket is opened for each one. Schema violations are rejected at the boundary rather than corrected downstream.

Impact assessment checklist

  1. Confirm that monitoring and alert thresholds still apply to the changed flow.
  2. Confirm the rollback approach and who decides to use it.
  3. Agree a test window with each consuming team before the change goes live.
  4. Confirm data classification and retention are unaffected.
  5. Check that reconciliation counts can still be produced after the change.
  6. Tell the service desk about the change and any expected support impact.
  7. Check whether the batch window or trigger dependencies change.

When the extract fails

  1. Check the channel or connection status between the two systems.
  2. Record the actions taken in the interface log.
  3. Look for parked or rejected records and note their keys.
  4. Re-run the delivery once the cause is fixed; the process is safe to repeat.
  5. Raise an incident if the delivery misses its business deadline.
  6. Confirm the target has loaded the delivery and reconciled the counts.
