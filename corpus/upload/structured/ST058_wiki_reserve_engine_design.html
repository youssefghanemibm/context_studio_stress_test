Claims Hub : reserve-engine Design

Created by Daniel Achebe, last modified by Daniel Achebe on Mar 09, 2026

APPROVED Design of reserve-engine, the Claims Hub service for case reserves and reserve movements.

Rename

reserve-svc was renamed reserve-engine on 2026-02-10 (CHUB-233, ADR-019). The repository path, namespace labels and Terraform module moved with the rename; the namespace stays chub-reserve. Event topic reserve.changed.v1 was retired and replaced by reserve.changed.v2.

Responsibilities

  • Case reserves, reserve movements, Tier-3 review scheduling, indexation and currency revaluation
  • Authority checks on reserve movements (BR-RSV-003 v3)
  • Large loss flagging for Reinsurance (BR-RSV-011 v2, LLNT £250,000)
  • Synchronisation with CLARA reserve movements through CLX-IF-049 until Wave 2

Audit finding IA-25-07

CLRGL090 (year-end revaluation) updates CLR.T_RESERVE without writing a reserve movement (internal audit finding IA-25-07; CHUB-284 closed as Won't Do). reserve-engine records revaluations as RV movements instead (DEC-005, 2026-03-05). CLRRS150 writes movements only.

Parallel run

The reserve parallel run compares CLARA and reserve-engine reserves daily from 2026-03-02 to 2026-08-28 (CHUB-241). CLARA job CLRDRSV9 (program CLRRS210) produces the CLARA side of the comparison.

Movement flow

Claims Handler -> reserve-engine: POST /reserves/{claimId}/movements
reserve-engine -> reserve-engine: authority check (BR-RSV-003 v3)
reserve-engine -> PostgreSQL: insert reserve.reserve_movement, update reserve.reserve
reserve-engine -> Kafka: reserve.changed.v2 (outbox)
gl-posting-svc <- Kafka: reserve.changed.v2
CLARA CLX-IF-042 -> MQ -> CLX-IF-049 bridge -> claims.reserve.movement.v1 -> reserve-engine

Operational runbook

  1. Confirm the target has loaded the delivery and reconciled the counts.
  2. Check the channel or connection status between the two systems.
  3. Re-run the delivery once the cause is fixed; the process is safe to repeat.
  4. Escalate to the interface owner if the cause is not clear.
  5. Record the actions taken in the interface log.
  6. Inform the consuming teams if delivery will be late.

Test approach

  • A schema version mismatch is detected and the record is parked.
  • A restart after failure resumes without losing or repeating records.
  • A resent record with the same business key does not create a duplicate.
  • A field at its maximum length is carried without truncation.
  • A late upstream delivery holds the dependent processing until it arrives.
  • A malformed record is rejected at the boundary and logged with its key.
  • Characters outside ASCII (æ, ø, å, ä, ö) survive the round trip.

Design principles

  • All writes are idempotent on the client-supplied request key.
  • Configuration is externalised and effective-dated where business rules require it.
  • Breaking changes go through a new major version; the old one is retired after consumers move.
  • The service owns its data and exposes it only through its API and events.
  • Contract tests run in the pipeline against the published API and event schemas.
  • Time stamps are stored in UTC and rendered in the user's locale.
  • Health and readiness endpoints are exposed for the platform probes.
